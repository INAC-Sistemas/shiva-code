# Agent Note: VPS-owned profiles (plugin-manager / dsh-profiles / the `profile` preset)

Status: implemented

## Problem

"Profile" existed twice, and neither instance narrowed what an agent loaded.

`plugins/dsh-profiles` kept `~/.dsh/profiles/profiles.json` on the machine, behind routes with no authentication and a `sameOrigin()` that returned `true` when no `Origin` header was present. Its `preset` and `skills` fields were written and never read by anything. Its only effect was `window.__profileTabEnabled(tabId)`, published synchronously **before** its own bootstrap fetch resolved, so any client half that registered its tab first got `true` — a fail-open race. Seven plugins consulted it right before `betterSidebar.registerTab`, and an eighth (`dsh-sidebar-qa`) appeared in the picker's checkbox list without ever consulting it at all.

Even where the helper worked it hid a tab while the plugin stayed loaded: its tools registered, its routes served, its prompt sections assembled.

The VPS half was a single library for the whole installation. `plugins/skill-library/index.ts` filtered on `published` alone, and the catalog route's own comment said a `403` there "seria uma regra nova".

The model-facing leak was narrower than it looked, and worth stating precisely, because it decided the design. `packages/bundle/web-app/cordis.patch.yml` **already** disables every model-facing base row and mounts `agent-presets`, so the Web surface already put the agent plane behind presets. What still reached every agent regardless of preset were four host-plane rows in `desktop/build/dsh-desktop.patch.yml`: `dsh-skill-library` (a `registerProvider` on the host context files into the **global** skill layer), `dsh-vps-status` (same, for `tools`), plus `dsh-better-sidebar`'s eight `terminal_*` tools and `dsh-openviking`'s MCP tools.

## Decision

**The plugin manager owns the roster; the client materializes it.** A profile is rows in Postgres — `Profile` with a `plugins String[]` and a `ProfileSkill` join to `LibrarySkill` — and `User` gains its first relation.

**The active profile is a column, not a token claim.** `User.activeProfileId`. Switching is one write: no token is minted, none is revoked, and the next request from any device resolves the new profile. The alternative — a `profileId` claim plus an exchange route — needed claim projection in three places, revoke-on-exchange to stop the old profile's token from still reading its skills, an `exp` cap so re-exchange could not extend the 24-hour policy forever, and a client that rewrote its stored credential. All of that bought per-device profiles; the column buys per-user profiles for one `UPDATE`. **Per-user, not per-device, is the accepted cost** and belongs in the product copy.

**A profile only narrows.** `readActiveSpec` and the library both filter the selection by `published` — the same predicate — so no profile can reach a row the published library did not already grant. That invariant is what makes it safe for every user, guest included, to edit their own profiles, and it is why the `plugins` and `skills` filters are read-time rather than write-time (an admin may unpublish something temporarily without destroying selections).

**No profile ⇒ empty catalog.** Not the full library. The shell is untrusted code: if "no profile" read everything, a client would simply never select one. The narrowing is non-additive — the first such change in this codebase — and it is safe in *shape* because `plugins/dsh-skill-library/src/wire.ts`'s `parseCatalog` requires only `body.skills` to be an array, ignores the top-level `revision`, and the provider already has `AUTHORITATIVELY_EMPTY` as a cacheable first-class state. The migration's hand-written backfill exists so no existing user lands in that state.

**The server sends identifiers, never composition text.** `cordis.yml` evaluates `!!js` under `config` and `disabled`; YAML served over the network would be remote code execution on the user's machine. `PLUGIN_ROWS` in `plugins/dsh-profiles/src/wire.ts` resolves a name into a row, and it lives in the client's own source. An unknown name is dropped.

**Conditional rows in a shipped preset, not generated YAML.** The first design generated `<dshHome>/.agent-presets/profile-<slug>/agent.cordis.yml` per profile. Generation existed only to avoid a restart — and a restart is unavoidable anyway for host-plane rows, so it bought nothing. `apps/cli/config/agent-presets/profile/agent.cordis.yml` is `standard` plus two rows carrying `disabled` expressions over `$DSH_PROFILE_PLUGINS`. This keeps `agentPresets.copy()` as the only authoring write ("no caller ever supplies composition text"), avoids the never-reclaimed standing generations of `ensureStanding`'s TODO, and keeps every `!!js` in a versioned file of ours.

**Two planes, two fallback directions.** Inside the preset, an unset `$DSH_PROFILE_PLUGINS` disables the row — that preset exists only for profile deployments. In the desktop patch it *enables* the row, because a first boot before any login, a dev run and the CLI must all show a working app. The asymmetry is only acceptable because the plane the model sees fails closed: an agent that joins no preset resolves the empty global layer, and `agent-presets`' invariant companion fails `system-prompt/assemble`.

**`window.__profileTabEnabled` is deleted with nothing replacing it.** A profile now decides what *loads*, so a plugin outside it has no tab to hide.

## Alternatives considered

**A `profileId` claim in the token, with a `POST /api/auth/profile` exchange.** The design this replaced, and the one that reads as obvious. It needed the claim projected in three places (`RawClaims`, `TokenClaims`, and the field-by-field projection in `decodeTokenClaims`, where a missing line drops the claim silently), revoke-on-exchange so a switch did not leave the previous profile's token still reading its skills, an `exp` cap so re-exchanging every 23 hours could not extend the 24-hour policy indefinitely, and a client that rewrote its stored credential and could strand itself by failing to persist the new one. All of that bought per-DEVICE profiles. `User.activeProfileId` buys per-user profiles for one `UPDATE`, and leaves `dsh-login` untouched.

**Generating `<dshHome>/.agent-presets/profile-<slug>/agent.cordis.yml` per profile.** Rejected once the restart was accepted. Generation existed only to make a switch take effect without restarting — but a host-plane row can only be turned off by not loading, so the restart is unavoidable anyway and the generator bought nothing. It would have cost a second authoring path beside `agentPresets.copy()`, whose whole premise is that no caller supplies composition text; a new standing generation per roster change, none of them ever reclaimed (`ensureStanding`'s TODO), each holding live `skill-filesystem` watchers; and a `!!js`-free-output assertion in the generator to keep server data away from the composition evaluator. Conditional rows in a shipped, versioned file need none of it.

**`ToolRuntime.restrict()` at runtime instead of moving rows off the host plane.** It is the only subtractive operation the three scope-aware registries have, and it is not enough on three counts. It covers tools alone — a preset that excluded `dsh-flowglass` would still get its prompt section, and one that excluded the library would still get its whole catalog, because `SystemPrompt.assemble` and `SkillRegistry.collectFresh` both seed from the global layer with nothing to subtract. It only hides: the plugin still ran its `apply`, still holds its watchers, its Python server, its routes — and "must not load" was the requirement. And it **throws** on a name that is not registered, so a deny list naming `terminal_create` fails the mount on any build where `dsh-better-sidebar`'s `agentTerminalTools` setting is off.

**Serving the full library to a token with no active profile.** Compatible, and self-defeating: the shell is untrusted code, so it would simply never select a profile. A softer variant — "full library only when the user has zero profiles" — was rejected too, because it reopens the same hole for anyone who deletes their profiles and makes a security property depend on data. The migration backfill and the seed exist so that nobody is in that state.

**A `Plugin` table on the VPS instead of the `KNOWN_PLUGINS` constant.** The plugin set is a property of the client RELEASE — the VPS installs none of them — so a table could only mirror a constant while adding a seed path, a join table, and a class of "catalog row drifted from what the client ships" bugs. `plugins/prototype`'s `KNOWN_OPS` is the same call already made in this codebase. The cost is that a new client plugin needs a deploy to appear in the panel; a seeded table would have needed a seed edit and a restart, so the difference is smaller than it looks.

**Keeping `window.__profileTabEnabled` alongside the composition gate.** It would have kept the sidebar honest for host-plane plugins between a profile switch and the restart. Rejected because two mechanisms answering "is this plugin in my profile" drift, and the helper's failure mode is the bad one: it is published before its own bootstrap fetch resolves, so it answers `true` to whoever asks first. A gate that fails open is worse than no gate, because it reads as enforcement.

## Consequences

- **Only `ToolRuntime.restrict()` subtracts, and only tools.** `SystemPrompt.assemble` seeds sections from the global layer and `SkillRegistry.collectFresh` starts `[global, ...chainLayers(scope)]`; neither has a subtractive operation. So "the row is not in the host composition" is the entire mechanism — there is no runtime filter to fall back on. `apps/web/tests/preset-scope-isolation.snapshot.ts` asserts that failing direction on purpose, next to the two isolation facts.
- **`dsh-login` is untouched.** Because the token does not change, `dsh-skill-library`, `dsh-prototype` and `dsh-vps-status` became profile-scoped with no change of their own: each already resolves the login grant per operation and never caches.
- **A host-plane change costs a restart**, and a restart ends running sessions. `hostPlaneDiffers()` asks only when a host row actually changed.
- **A session already open keeps its composition.** The gateway answers `agent-preset-locked` for any agent that produced something; the picker says so rather than failing silently.
- **`verify-cordis-config` gained two obligations.** `validatePresetPlaneSeparation` now also reads `desktop/build/dsh-desktop.patch.yml`, so a row returning to the desktop insert after moving into the preset fails CI. `validateProfilePlaneDeclared` makes every desktop row declare its plane — `HOST_ALWAYS` or a `disabled` expression naming both `DSH_PROFILE_PLUGINS` and its own plugin name. Adding a plugin row without declaring a plane is exactly how the `dsh-skill-library` leak survived unnoticed.
- **`dsh-better-sidebar`'s `terminal_*` tools still sit in the global layer.** It is the chassis every other tab plugs into, so its row cannot move; the honest fix is splitting the package so a `dsh-better-sidebar/agent-tools` entry point registers the eight tools from a preset row, reading the PTY registry the host half publishes — the pattern the repo already documents for `tasks`/`goals`. Deliberately not in this change. `tools.restrict()` is not a stopgap worth taking: it only hides schemas while node-pty stays loaded, and it *throws* on an unknown name, so a deny list breaks on any build where the `agentTerminalTools` setting is off.
- **Scopes are not authority boundaries** (`packages/core/scope/README.md` says so outright). Which plugins load is a composition boundary; the user can edit their own composition, pass `--patch`, or set `$DSH_PROFILE_PLUGINS` by hand. The enforced half is the server's: a skill outside the active profile is never served to that token.
- **`headless` is out of scope** — it composes no presets, so every model-facing row is host-plane there and there is no boundary to draw.
- **A published skill reaches nobody until it is ticked into a profile.** A real operational cost. The escape hatch, if it bites, is a bulk "add to all my profiles" action on the skills page — deliberately not in this change, because two ways to express "everything" would drift.
- **`prisma/skills/10-profiles/SKILL.md` described the old client-local model** and was rewritten. Its seeded row had to be updated separately: `seedSkills` upserts with `update: force ? {…} : {}`, so editing the file changes nothing in an existing database, and `--force-skills` would discard panel edits to all twelve seeded skills.
