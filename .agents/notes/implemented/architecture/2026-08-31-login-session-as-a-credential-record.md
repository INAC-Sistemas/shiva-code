# Agent Note: the login session as a credential record (dsh-login / dsh-vps-status)

Status: implemented

English | [中文](2026-08-31-login-session-as-a-credential-record.zh.md)

## Problem

Two out-of-tree plugins authenticated against the same VPS in two unrelated ways. `dsh-login` obtained a per-user token and kept it in the browser (`localStorage`, published as `ctx.loginSession`); its host half deliberately held no session state. `dsh-vps-status` — a host-only tool the model calls — sent a static `Bearer $VPS_TOKEN` machine credential read from `.env`. There was no path by which a host-side plugin could act as the signed-in user, so every model-initiated request to the VPS was anonymous with respect to who asked for it, and the shared token sat in `process.env` where anything in-process could read it and any spawned command could inherit it.

A second gap sat on the browser side: nothing detected a dead token. `sessionTtlMs` defaults to `0`, so the store's expiry timer never armed, and the token's real expiry is the login service's business. A user whose token had been revoked kept looking signed in until some call happened to fail.

## Decision

**The credential seam is the seam.** No new `ctx.vpsAuth` service: `ctx.credentials` already has a Service Definition, a provider, and consumers, and CLAUDE.md's rule for splitting a seam ("only when roles evolve independently") is not met — there is no provider role for "the VPS token" that is not already the credentials provider. A corollary removes most of the machinery a service would have needed: the seam's own rule is that consumers re-resolve per operation and never cache, so there is no `credentials/record-updated` listener, no cache, and no `subscribe` on the host side. What consumers share is a library, not a service.

**The host's copy is a `GrantRecord` at `dsh-login/session`.** The authenticate handler already sees the token on its way back to the browser, so it writes the record there — no browser→host bridge route exists or is needed. The key's scope is `dsh-login` because the seam addresses a record by its *owner's* registered plugin name; this plugin is the only writer, so the module owning the key, the payload, the expiry rule and the `Bearer` construction ships inside `dsh-login` and is published as the `dsh-login/vps-auth` subpath. Host-side consumers add `dsh-login` as a peer dependency and import it — the "structural types, no cross-plugin imports" precedent in `plugins/` exists only because the *browser* bundle's purity gate forbids platform value imports, and does not transfer to the host plane.

**The record is not a mirror of the browser session.** It is the host's own copy of the same grant, written by the handler that produced it and retired by the same sign-out. Stating that dissolves most of the "drift" question into properties to document rather than state to reconcile.

**Returning to the gate is ending the session.** `LoginGate` renders from the store through `useSyncExternalStore` and returns `null` while a session holds, so nothing needs a router or a redirect. Two triggers were added: `ctx.loginSession.authorizedFetch`, which owns the `authorization` header and signs out on `401`/`403`; and a revalidation against `config.validateEndpoint` on boot and on tab focus, through a new `GET /login/api/validate` route.

**`ValidateResult` is discriminated, not a boolean** — `{ ok: true } | { ok: false, reason: 'rejected' | 'unreachable' }`. Only `rejected` ends a session. Collapsing the two would turn an outage of the login service into a mass sign-out, which is the mirror image of the failure the existing sign-out ordering already guards against: a service that cannot be reached must neither trap a user inside the app nor throw them out of it.

**A login the host cannot record fails the login** (`grant-storage`, HTTP 500). The alternative — browser signed in, host copy missing — is the silent half-state where the app reports success and then fails every host-side request.

## Consequences

- `$VPS_TOKEN` is gone from `.env`, from `dsh-vps-status`'s patch, and from its README. `config.headers` survives for gateway keys and tenant ids, but an `authorization` row is now **rejected at load**: that header has one source, and a leftover static token would silently shadow the signed-in user.
- `dsh-vps-status` gains a hard peer dependency on `dsh-login`, and a profile mounting the tool without the gate has a tool that can never authenticate. This removes the "point it at any host with its own static token" capability its own multi-host example advertised. The reintroduction path, if it is ever wanted, is a `auth: 'session' | 'headers'` config field — deliberately not in this change.
- Neither plugin hard-injects `credentials`: both resolve `ctx.get('credentials')` per operation with a documented refusal, matching the seam's optionality and `llm-pi-ai`'s idiom. Presence is not decidable at `apply` (mount ordering), so `dsh-login` logs a warning there and decides at the login attempt, the earliest resolvable point.
- **The user's bearer now lives on disk** (`$DSH_HOME/.credentials.yaml`, mode `0600`, cross-process locked), surviving the browser closing and the machine restarting. That is what lets host-side tools survive a harness restart and lets a headless run act as the signed-in user after one sign-in. It is also a real change in exposure, chosen deliberately; `sessionTtlMs` stays at its `0` default, so the record carries no expiry of its own and is retired only by a sign-out or a negative revalidation — both of which originate in a browser. A finite `sessionTtlMs` is the one-line change that would retire both copies unattended.
- Offsetting that: the credential store is **never materialized into the process environment**, and no model-visible tool reads record payloads. Moving off `process.env` is a net reduction in exposure to spawned commands and in-process readers.
- **One record, one identity, one `$DSH_HOME`.** Two people sharing a harness home, or a `dsh --profile headless` run beside the web UI, all act as whoever signed in last. This matches the harness's existing single-user assumptions (settings, sessions, identity), but it is broader than "the tab that signed in" — and the old `$VPS_TOKEN` had the same blast radius while *looking* like a machine credential, where this one looks like a user credential and is not scoped like one.
- Sign-out is **compare-and-delete**: the same-origin fence is a cross-site defence, not authentication (a caller with neither `Sec-Fetch-Site` nor `Origin` passes), so an unconditional delete would let any local process end the host's session. The seam offers no compare-and-delete primitive — `modifyRecord` returning `undefined` means *leave untouched*, not *delete* — so a sign-in landing between the read and the delete loses its fresh record. Self-healing: the browser still holds the token and the next request re-publishes.
- `modifyRecord` takes no signal and `DOCUMENT_LOCK_WAIT_MS` is 30 s, so `/login/api/authenticate` can stall that long while another writer of `.credentials.yaml` (an `llm-pi-ai` OAuth refresh) holds the document lock. Accepted; a second deadline would abandon a write mid-flight.
- `isUnloading` is **not** used: nothing here re-registers on teardown (the routes are plain `ctx.effect` registrations), and finishing an in-flight HTTP response during teardown is correct.
- `revalidateIntervalMs` is enforced on the **host**, because the client bundle receives no plugin config. The memo caches only a pass, for one token, so a token revoked at the login service keeps passing revalidation until the window elapses. That is what the rate limit buys; the window bounds how stale an answer can be.
- A `401` from a host-side tool does **not** delete the record and does not end the browser's session. A transient upstream fault would otherwise wipe a good session; the browser's own revalidation is what retires it.

## Alternatives considered

- **A dedicated `dsh-vps-auth` seam plugin owning `ctx.vpsAuth`** — rejected on the seam's own addressing rule. A `CredentialKey`'s scope must be the registered name of the plugin that *writes* the record, and `dsh-login` is the only writer; a separate package owning the key would file records under a scope whose named owner never writes them. It would also be a second seam over a fact the credentials seam already models.
- **An in-memory host holder, rehydrated by a browser→host publish route** — rejected twice over: it recreates the bridge the design avoids, and it would hand any same-origin caller (the fence admits header-less local processes) a way to *set* the host's token. It also loses the harness-restart and headless cases the durable record gives for free.
- **A `persistSession: false` / memory-only switch on `dsh-login`** — rejected: durability is the credential *provider's* job, and a second storage path inside the consumer would duplicate the provider role. The correct shape, if it is ever wanted, is a `@deepseek-ai/dsh-credentials-memory` provider mounted in place of `-local` (`packages/credentials/credentials/tests/memory.ts` is already a complete implementation to promote) — a separate `packages/` change.
- **Local expiry via a finite `sessionTtlMs`, and propagating a host-side `401` to the browser** — both considered and left out at the user's direction. The first is recorded above as the one-line follow-up; the second needs a host→browser channel that does not exist.
- **Logging a failed record write and signing the browser in anyway** — rejected: it produces exactly the half-state the credential design note warns about, where a login reports success and every host-side request then fails.
